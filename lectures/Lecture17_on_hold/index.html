Mutation testing

Quick recap

  • Line and branch coverage
  • Specification and structural testing
  • Test smells and anti-patterns

The claim

Coverage asks whether the test ran the line. Mutation testing asks whether the test would have noticed if the line were wrong.

Those are different questions, and only one of them is about your tests.

1. Something you have already seen

bool eligible(bool member, int amount) {
    return member || amount > 1000;
}

EXPECT_TRUE (eligible(true,  500));
EXPECT_FALSE(eligible(false, 500));

Both outcomes of the decision are reached. Decision coverage: 100%.

Now delete half the rule:

return member;                     // `|| amount > 1000` removed

Both tests still pass. The suite did not notice that the program changed.

Give it a name

That deleted operand is a mutant — the same program with one small, deliberate change. The suite stayed green, so the mutant survived.

A survivor is not a vague worry. It is a specific missing test, and it tells you which one: eligible(false, 1500).

Write that test and the mutant dies.

2. The method

  1. Change the program in one small way
  2. Run the suite
  3. Suite goes red → the mutant is killed
  4. Suite stays green → the mutant survived
Term Meaning
Mutant the program with one deliberate change
Mutation operator the rule that produced the change
Killed at least one test failed. The suite noticed
Survived every test passed. The suite did not
Mutation score killed ÷ (total − equivalent)

A coverage report tells you what the tests touched. A mutation score tells you what they would defend.

3. The operators

Mechanical. No judgement, no cleverness — which is why a machine can generate them.

Operator Change Example
Relational swap a comparison score > high → score >= high
Arithmetic swap an operator x + 1 → x - 1
Logical swap a connective a && b → a \|\| b
Constant replace a literal cellcount → 0
Statement deletion remove a line drop the guard
Return value invert a result return true → return false

Six operators over a few hundred lines produce hundreds of mutants. That is the point: the machine proposes, and every survivor is a question you have to answer.

4. A real suite, measured

The snake harness in docs/code/snake_seam/. Nineteen tests. All of them pass.

Eight mutants, one at a time, rebuild and re-run each:

# Mutation Outcome
1 sc++ deleted killed
2 if (addb == true) → != true killed
3 eid returns false on a match killed
4 ct - lup >= in → > in survived
5 all four direction guards deleted survived
6 if(eid(head, body)) → if(false) survived
7 x == cellcount → x >= cellcount survived
8 y == -1 → y <= -1 survived

Three killed out of eight. A mutation score of 37.5%, from a suite that is entirely green.

Survivor 6 is the one to look at

if(eid(s.body[0], hb))        // does the head touch the body?

Replace the whole condition with if(false). The snake can now pass straight through itself. Nothing detects it.

All nineteen tests still pass.

Read the test names and you find out why:

EidFindsElement            SnakeUpdateMovesWithoutGrowing   MainLoopKeyPresses
EidMissingElement          SnakeUpdateGrowsWhenAddb         MainLoopEatsFoodAndScores
EidEmptyDeque              SnakeDrawDrawsEachSegment        MainLoopHitsRightWallAndResets
EventTriggerFires...       SnakeResetRestoresDefaults       MainLoopHitsTopWall
FoodConstructorLoads...    GoResetsScoreSnakeAndFood        ...

Walls, food, score, growth, reset. Not one test says the snake dies when it hits itself. That is the central rule of the game.

Nobody noticed, because every metric the suite reports was green.

Survivors 4 and 5

4 — >= became >. The clock now fires one instant later. No test puts the elapsed time exactly on the boundary, so no test can tell. A missing boundary case, named precisely.

5 — the direction guards. With them deleted the snake can reverse into itself. There is a test called MainLoopKeyPresses that presses all four keys; it asserts only that main returned 0.

Both are ordinary missing tests. You can write them this afternoon.

5. Survivors 7 and 8 are a different problem

if (s.body[0].x == cellcount || s.body[0].x == -1)     // original
if (s.body[0].x >= cellcount || s.body[0].x == -1)     // mutant

No test kills it. Before you write one, ask whether a test could.

The head moves one cell per step, and the check runs immediately after the move. So x can reach cellcount and can never overshoot it. Under that invariant, == and >= cannot ever disagree, and no test can distinguish them.

That is an equivalent mutant: a changed program with unchanged behaviour. No test kills it, and no test should.

Why this is the hard part

Notice what deciding it required: an argument about an invariant that appears nowhere in the code. The snake moves one cell at a time because of how update happens to be written, not because anything says so.

Change the game to allow a dash move, and mutant 7 stops being equivalent — it becomes a bug.

Detecting equivalent mutants in general is undecidable. There is no tool that will sort your survivors for you.

Which means the score is a judgement

Killed Total Score
Counting every mutant 3 8 37.5%
Excluding 7 and 8 as equivalent 3 6 50%

Same suite, same eight mutants, two different numbers — and the difference is a human decision that took a minute of reasoning.

Do not chase 100%. It is not a target you failed to reach; it is a number that does not mean anything.

6. What it costs, and what it misses

Cost. Every mutant runs the whole suite. A hundred mutants is a hundred runs. In practice: mutate only files that changed, sample the operators, run it nightly rather than on every commit.

What it misses. Two different diseases, and this tool sees one of them:

Symptom Diagnosis Does mutation testing find it?
A mutant survives a missing test yes — that is exactly what it reports
A test breaks when you rename a variable or change a constant a fragile test no. Blind to it

A suite can score well and still be full of tests that fail for no reason. Mutation testing has nothing to say about those.

The tools

Language Tool
Java PIT
Python mutmut, cosmic-ray
C / C++ mull

The table in §4 was produced by hand: eight edits, eight rebuilds. The technique does not need a tool. It needs you to be willing to break your own code on purpose.

7. Exercise

void saveHighScore() {
    if (score > highScore) {
        ofstream outFile(HIGH_SCORE_FILE);
        if (outFile.is_open()) {
            outFile << score;
            outFile.close();
            highScore = score;
        }
    }
}

On paper, no compiler:

  1. Apply three operators — one relational, one statement deletion, one constant
  2. For each, decide: would a test you would plausibly write have caught it?
  3. Find one mutant you believe is equivalent, and write the argument for why

Back to the claim

The module has asked several times how to choose tests: from the specification, from the structure of the code, from the dependencies that got in the way.

This is the only technique that turns the question around and asks what the tests are worth.

Coverage is a measure of your code. A mutation score is a measure of your tests.

Nineteen passing tests, and the snake could eat itself.
