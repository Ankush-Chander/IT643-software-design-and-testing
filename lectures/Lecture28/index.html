Deciding what not to read

Quick recap

  • Legacy code is code without tests: cover first, then let the agent modify

Agenda

  • Line count is not risk
  • Predict the blast radius before the agent runs
  • Keep the diff small: sprout and wrap
  • Risk-based review: what to read line by line, what to trust

Two diffs, one request

Same game, same request to two agent runs: "Press P to pause, P again to resume." Run B was also told: "put it in a new class; change at most one existing line."

Run A Run B
Lines added 13 32
Lines changed 1 1
Characterization tests 5 pass 5 pass

You can review only one carefully. Which one is riskier?

Answer

Run A, with fewer than half the lines.

Run A Run B
Existing functions touched 4: drawBoard, processInput, restart, run 1 line in processInput
New code spread through the old code one new class, one new method

Risk is about how much of the existing code changed, not how many lines arrived. New code beside old code can be read on its own. Edits inside old code have to be read against everything around them.

Predict before you prompt

Before asking for a change, sketch what it can affect. Then compare the sketch with the diff. Anything outside the sketch is the first thing you read.

Effect sketch: pause

The game loop:

while (!gameOver && running) {
    processInput();
    update();
    drawBoard();
    usleep((int)(baseDelay * speedFactor));
}

What each call can change:

processInput() ──► snake direction, running, restart()
update()       ──► snake, food, score, highScore, speedFactor, gameOver
drawBoard()    ──► the screen

Pause obviously stops update(). What else does it have to decide?

Answer

Three decisions nobody asked for, one per arrow:

While paused... Decision
can the player still steer? processInput() changes direction
does R still restart? processInput() calls restart()
is the screen redrawn? drawBoard()

The request said none of this. The agent will decide all three. Your sketch tells you to check how.

Prediction vs diff

What each run actually decided:

While paused... Run A Run B
steering ignored ignored
R restarts ignored ignored
screen redrawn yes, every 50 ms no: it waits inside processInput()

And Run A touched one function the sketch didn't predict: restart().

Is that a problem?

Answer

Read it and see. It's one line: paused = false;, so a new game never starts paused. Reasonable.

The point isn't that restart() was wrong. It's that it was outside the prediction, so it's the line you read first, and possibly the only one.

Keep the diff small

New code beside old code, not inside it. Feathers calls these sprout and wrap.

Sprout class

Run B's pause lives in a new class, with no terminal I/O:

class PauseController {
    bool paused = false;
public:
    static bool isPauseKey(char k) { return k == 'p' || k == 'P'; }
    bool handleKey(char k) {            // true if k was a pause key
        if (!isPauseKey(k)) return false;
        paused = !paused;
        return true;
    }
    bool isPaused() const { return paused; }
    void reset() { paused = false; }
};

And the one existing line that changed:

-        char control = readControl();
+        char control = filterPause(readControl());

What can you test now that you couldn't in Run A?

Answer

PauseController on its own: press P, it's paused; press P again, it isn't; press W, nothing changes. No game, no terminal, no #define tricks.

In Run A, pause is a bool spread across four functions. Testing it means driving the whole game.

Wrap method

Keep the old method's body, give it a new name, and put the new behaviour around it:

void update() {                // same name: every caller is unchanged
    if (paused) return;        // new behaviour
    advanceOneFrame();         // the old update(), renamed, not edited
}

Sprout or wrap: when would you pick wrap?

Answer
Use When the new behaviour...
sprout is a new thing, with its own logic to test (pause state, key handling)
wrap happens before or after something existing, every time it runs (skip, log, time)

Either way, the old code isn't edited, so the characterization tests still say exactly what they said before.

As an instruction to an agent

Prompt What you get
"Add pause." a correct-looking change, spread through 4 functions
"Add pause in a new class. Change at most one existing line." the same feature, in one new class and one changed line

One extra sentence in the prompt, and the review got smaller.

Risk-based review

You can't read every line an agent writes. Choose what to read.

Read less, in the right places

Instead of reading Read
the whole diff which functions it touches; compare with your sketch
the implementation the tests: do they pin the behaviour that matters?
every line equally the risky paths, line by line; skim the rest

What always gets read line by line

  • money, payments, scores that count for something
  • authentication and permissions
  • deleting or migrating data
  • loops that wait, block or retry: they decide whether the program can hang

Which part of Run B gets a line-by-line read?

Answer

filterPause(), the waiting loop:

while (pause.isPaused() && running) {
    char c = readControl();
    if (!c) { usleep(50000); continue; }
    if (c == 'q' || c == 'Q') { pause.reset(); return c; }
    pause.handleKey(c);
}

The whole game sits inside this loop while paused. Can it exit? Only on P or Q. Is that what you want? Probably. But this is the line where "probably" has to become "checked". PauseController itself is safe to skim.

💬 Review Run A without reading the body

You get only this:

snake.cpp | 14 +++++++++++++-
Game fields     +1   bool paused = false;
drawBoard()     +3 -1
processInput()  +3
restart()       +1
run()           +5
tests: 5 characterization tests on update(), all pass
  1. Is the blast radius what you predicted?
  2. Do the tests pin what matters?
  3. Which hunk do you read line by line?
Step 1 — Answers
  1. No. restart() is outside the sketch. Read it first. It's one line.
  2. No. The tests pin update(). The behaviour change is in processInput(), and nothing watches it.
  3. processInput(). It changes what keys do, and no test covers it.
Step 2 — What the line-by-line read finds 
if (control == 'p' || control == 'P') { paused = !paused; return; }
if (control == 'q' || control == 'Q') { running = false; return; }
if (paused) return; // ignore steering/restart while paused

Restart is now ignored while paused. Nobody asked for that. It may be fine. But it is a decision, so either accept it or pin it with a test, so that it doesn't change again unnoticed.

drawBoard() and run(): skim. They show a message and keep the loop polling.

The rule to keep

Read what changed in old code, what the tests don't cover, and what can hang. Skim the rest.

Before the agent runs After
sketch the effects compare the touched functions with the sketch
ask for sprout or wrap read old-code edits before new code
read line by line only where the tests don't reach, or where it's risky
